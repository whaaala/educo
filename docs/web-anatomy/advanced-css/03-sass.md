## Lecture 12 — what Sass is

**Sass is a CSS PREPROCESSOR** — an extension of CSS that adds what plain CSS lacks for a large project (one file of
thousands of lines with no reusable pieces and no logic becomes unmanageable), without changing how CSS works. You write
Sass; a **compiler** turns it into ordinary CSS; the browser only ever sees the CSS. (Less and Stylus are the others;
Sass is the most used.)

**What it adds:**
- **variables** — reusable values (colours, font sizes, spacing);
- **nesting** — selectors inside selectors, less repetition;
- **operators** — arithmetic in the stylesheet;
- **partials and imports** — the CSS split across many files, compiled into one (the 7-1 pattern, lecture 9);
- **mixins** — reusable pieces of CSS;
- **functions** — like mixins but they RETURN a value;
- **extends** — selectors inheriting shared declarations;
- **control directives** — conditionals and loops (not covered: framework territory).

**Two syntaxes:** the original indented **Sass** (no braces, no semicolons) and **SCSS** ("Sassy CSS", looks like CSS —
the course uses this one).

**For the builder:** it has no Sass and does not need it — the builder IS the preprocessor. Its stylesheet is GENERATED by
TypeScript (`lib/box-model.ts`, `lib/box-export.ts`, `lib/educo-ui/`), which already gives every Sass feature a native
equivalent, and the output is plain CSS like a compiled Sass file:
- variables → **CSS custom properties** (the `--eu-*` tokens, `--box-u`, `--bx-gut`) — better than Sass variables for a
  builder, because they live at RUN time: a theme switch or a reader's text size changes them without recompiling;
- mixins and functions → the shared **resolvers** (`childStyle`, `radiusCSS`, `gutterCSS`, `u()`, `remLen()`…), each one
  emitter for the canvas and the export;
- partials and imports → the CSS layers (tokens, base, components, per-block rules) compiled into one shared sheet;
- operators → `calc()` (run time) and TypeScript arithmetic (build time);
- nesting and extends → not needed: every block is ONE flat class (`bx-<id>`), BEM-flat by construction (lecture 9).
RULE M (Ponytail) says the same: a dependency is added only if nothing already does the job — here, nothing is missing.

## Lecture 13 — variables and nesting (a small navigation bar, in CodePen)

**The example.** `<nav>` holding a `ul.navigation` of three links (About us · Pricing · Contact) on the LEFT and a
`div.buttons` with two buttons (`btn-main`, `btn-hot`) on the RIGHT — the commonest header line there is.

**Variables** — `$name: value;` (always the `$`), defined once, used anywhere, changed in one place:
`$color-primary: #f9ed69` (yellow), `$color-secondary: #f08a5d` (orange), `$color-tertiary: #b83b5e` (pink),
`$color-text-dark`, `$color-text-light: #eee`, and not only colours — `$width-button: 150px` acts as a SETTING.
Variables emit no CSS; the compiler substitutes their values. `//` comments are Sass-only (not in the output).

**Nesting** — a selector written INSIDE another means "inside it": `.navigation { li { … a:link { … } } }` compiles to
`.navigation li` and `.navigation li a:link`. **`&`** writes out the selector path so far — needed to ATTACH a
pseudo-class or pseudo-element to the same element rather than to a descendant: `li { &:first-child { margin:0 } }` →
`.navigation li:first-child` (without `&` it would be `.navigation li :first-child`, which matches nothing intended);
`&:link`, `&:hover`, `&::after` the same. Advice: no deeper than three levels.

**The layout of the bar** (2017 way): `ul` items `display: inline-block` with `margin-left: 30px` (the first one 0),
the links uppercase, no underline; the list `float: left`, the buttons `float: right` — so the `nav` COLLAPSES to 0px
high (all its children float) and loses its background; fixed with a **clearfix**:
`&::after { content:""; clear:both; display:table }` nested in `nav`.

**Buttons:** shared rules on `.btn-main:link, .btn-hot:link` (padding, `inline-block`, centred text, pill radius, no
underline, uppercase, `width: $width-button`); per-button colours with nested `&:link` / `&:hover`; the hover colour
from a **colour function**: `darken($color-secondary, 15%)`, `lighten($color-tertiary, 10%)` — no second colour to pick.

**For the builder:**
- the bar itself → `HAVE`: a header line of links on one side and buttons on the other, spread across the line and centred
  (L-2, the user's "Header spreads"), menu links 2rem apart (1rem on a phone, F-1), built with FLEXBOX — no floats, so
  no collapsing parent and no clearfix (the visual formatting model, lecture 8e); a real Navigation component (dropdowns,
  the burger overlay) is a COMPONENT GAP already recorded in `docs/COMPONENT_GAPS.md`, outside the layout;
- variables → the `--eu-color-*` tokens, three brand colours plus text-dark / text-light like the lecture's;
- `darken` / `lighten` → the OKLCH colour scales (`--eu-color-primary-50 … -900`), computed and contrast-checked
  (rule 17); a hover that changes the colour is the *Brighten* hover effect — a "darken on hover" choice per button is
  part of the button component's variations, not layout;
- nesting / `&` → not needed: one flat class per block; `:hover` and `::after` are written by the resolvers.

## Lecture — Sass on the local machine: an npm script, compile, watch

- A `sass/` folder with `main.scss` (the `.scss` extension = the SCSS syntax). All of `style.css` is pasted in unchanged:
  valid CSS IS valid SCSS, which is why converting a project is easy.
- Colours become variables: `$color-primary` (green) with `$color-primary-light` / `$color-primary-dark`, `$color-grey-dark`
  (`#777`), `$color-white` — and Sass lets a hex variable go INSIDE `rgba($color-primary-light, .8)`, which plain CSS of
  the time could not.
- Compiling: an **npm script** in `package.json`, `"compile:sass": "node-sass sass/main.scss css/style.css"`, run with
  `npm run compile:sass`; the `-w` flag WATCHES the file and recompiles on every save (the terminal must stay open). The
  page never knows Sass existed — it loads `css/style.css`. Other npm packages prefix and compress CSS (later lectures).

**For the builder:** tooling only — it compiles nothing of this kind. Its one notable point has a modern native form the
builder can use directly: a colour token with an alpha is `color-mix(in oklch, var(--eu-color-primary) 80%,
transparent)` or relative OKLCH, at run time, so a theme change follows (the hero overlay gradient of lecture 1 in token
form).

## Lecture — live-server: reload the page on every change

`npm install live-server -g` — a GLOBAL install (usable in every project, not listed in `package.json`, not in
`node_modules`; on a Mac it may need `sudo`), unlike `--save` / `--save-dev` which install into one project. Run
`live-server` in the project folder: it serves the page over real HTTP (`127.0.0.1:8080`, no longer `file://`) and
reloads it whenever any file changes — with `npm run compile:sass` watching in another terminal, a Sass save recompiles
and the page refreshes by itself. Both processes keep their terminals.

**For the builder:** tooling only. Its own equivalents: `next dev` (hot reload, for the user's hands-on use) and, for
testing, the production build served by `next start` (CLAUDE.md rule 15 / RULE Q: never test on `next dev`).

## Lecture — Natours converted to Sass: variables + BEM-friendly nesting

- One more variable, `$color-black` (so "black" can later become a near-black in one place); hex variables inside
  `rgba($color-black, .2)` for the shadows. Font family / weight / line-height stay literal: they are written ONCE (on
  `body`), so a variable would add nothing.
- **Nesting with BEM.** Every element has its own one-class selector, so plain descendant nesting does not fit; instead
  `&` CONCATENATES onto the block name: `.header { &__logo-box {…} &__logo {…} &__text-box {…} }` compiles to
  `.header__logo-box` etc.; `.heading-primary { &--main {…} &--sub {…} }`; and the whole button in one block —
  `.btn { &:link, &:visited {…} &:hover {… &::after {…}} &:active {…} &--white {… &::after {…}} &::after {…}
  &--animated {…} }`. The compiled CSS is IDENTICAL to the hand-written CSS (flat, one class, low specificity) — the
  nesting only groups each BEM block in one place in the source.

**For the builder:** nothing to adopt — it generates the flat output directly; the lesson it confirms is that grouping by
COMPONENT (one block, its elements, its modifiers, its states together) is how its catalogue CSS is already organised
(`lib/educo-ui/components.ts`, one section per `eu-*` block). No gap.

## Lecture — the 7-1 architecture set up for Natours

`sass/main.scss` holds ONLY `@import`s, in this order: `abstracts/` (`_functions`, `_mixins`, `_variables` — output no
CSS) → `base/` (`_animations`, `_base`, `_typography`, `_utilities`) → `components/` (`_button`) → `layout/`
(`_header`) → `pages/` (`_home`). `themes/` and `vendors/` (Bootstrap's SCSS, an icon set, an animation library) stay
empty here. A **partial** is a file named `_name.scss`, imported as `@import "base/base"` (no underscore, no extension).

**How the existing code was sorted — and the judgement calls:**
- `_base`: the reset, `box-sizing`, and `html { font-size: 62.5% }` — kept in BASE, not typography, because it defines
  what 1rem IS for the whole page (a global sizing setting, not a type style);
- `_typography`: the `body` font rules and `.heading-primary` (arguably a component — filed under type because that is
  where one would look for a heading);
- `_animations`: the `@keyframes`;
- `components/_button`: the `.btn` block — reusable, independent, usable anywhere;
- `layout/_header`: the HEADER is filed as LAYOUT, not a component — the piece of the page every page will have, which
  holds the components together. ("There is no right and wrong" — but be consistent.)
- `pages/_home`: styles for this page only. The structure is for large multi-page sites; for a landing page it is
  deliberate practice, and ideally set up at the start, not retrofitted.

**For the builder:** the same split is its model, by construction rather than by folders —
- **layout regions** (header, main, aside, footer — `docs/web-anatomy/regions-and-education.md`) are built from blocks
  and the layout engine, and published as the landmark elements; the header is a region, not a catalogue component —
  matching the course's call;
- **components** live in one catalogue (`lib/component-catalogue.ts`, `lib/educo-ui/components.ts`), reusable on any
  page (RULE C);
- **base / abstracts / themes** = the base layer and the `--eu-*` tokens with the switchable themes (rule 17);
- **pages** — a page's own blocks carry their own `bx-<id>` rules; nothing page-specific leaks into the shared sheet.
No gap.
